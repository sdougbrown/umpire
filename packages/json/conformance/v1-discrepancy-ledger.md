# Umpire v1 discrepancy ledger

This ledger freezes the Umpire document v1 contract before the JSON Schema composition profile is implemented. It compares the normative decisions in the interop plan with the public meta-schema, `@umpire/json`, and `umpire-go-gen` as inspected on 2026-08-06.

The contract is normative. A row below records implementation drift or a fixture gap; it does not introduce a new v1 behavior. Stage 2 owns implementation alignment. Stage 1 adds the shared cases that make each row observable.

## Ledger

| V1-01 | `version` is required and equals numeric literal `1`; only the six declared top-level members are accepted. | Aligned: `required` and `additionalProperties: false` enforce this. | Drift: `validateSchema()` checks the version but does not reject unknown top-level members. | Drift: `Parse()` does not validate `version` and ordinary `json.Unmarshal` ignores unknown members. | `v1-baseline-failures`: `missing-version`, `wrong-version`, `unknown-top-level-member`. Add strict top-level validation to both runtimes. |
| V1-02 | `fields` is an object with at least one member. | Aligned: `minProperties: 1`. | Drift: checks only that `fields` is an object; an empty object passes. | Aligned for the public object shape: `Parse()` rejects zero field definitions. | `v1-baseline-failures`: `missing-fields`, `empty-fields`. | V1-08 | Omitted `prev` remains absent; an explicit empty prior snapshot remains an explicit `{}`. | V1-09 | Disabled fields always report `required: false`; enabled fields inherit the field definition's `required` flag. | Not applicable to evaluation. | Aligned in core evaluation: requiredness is gated by `enabled`. | Drift: generated status emission writes the declared required flag unconditionally. | `v1-baseline` cases `disabled-required-field-reports-required-false` and `enabled-required-field-inherits-required-flag`. ## Fixture conventions

`conformance/fixtures/v1-baseline.json` is an accepted public document and contains the normative status cases named in V1-06, V1-08, V1-09, and V1-10.

`conformance/failures/v1-baseline-failures.json` contains both kinds of rejection:

- The default is an implementation-level rejection whose `schema` remains valid against the public meta-schema.
- `metaSchema: "reject"` marks a document that the public meta-schema must reject as well. `validate.mjs` checks these cases with the same AJV contract used for the public schema.

The fixture IDs are intentionally stable. Runtime implementations must consume the fixture index rather than copying the examples into implementation-specific tests.

## Stage 1 disposition

Every row has an owner and a shared fixture or existing fixture reference. No row is an unresolved normative decision. Stage 1 does not change either sibling implementation, the JSON Schema composition profile, or the Umpire v1 semantics; it records the discrepancies and freezes the acceptance/rejection evidence for Stage 2.
